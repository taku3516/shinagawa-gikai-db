## 技術構成

- HTML / CSS / JavaScriptのみで動作し、フレームワークやビルドは不要です。
- データは`data/*.js`に分離し、`window.SHINAGAWA_DB`へ登録するスクリプト形式です。
- `index.html`を直接開く場合と、GitHub PagesなどのHTTPサーバーから開く場合の両方に対応します。

## 共通表示ファイル

読み込む順番が意味を持ちます。各ページの`<style>`は最後に来るので、
どうしても個別に変えたいページだけが上書きできる形にしてあります。

    site-theme.css → site-base.css → site-nav.css → site-controls.css
                   → site-mobile.css → site-a11y.css → ページの <style>

- `site-theme.css` — 配色とデザイントークン。標準配色と公共デザイン・ブルーはデジタル庁デザインシステムの値を使います。文字サイズの倍率`--fs`と、高コントラスト時の色の差し替えもここです。
- `site-base.css` — ページの骨格（`body`、`.container`、`h1`、`.lead`、`.hero`、`footer`、リンクなど）。以前はこれらが15ページに散らばって少しずつ違う値になっていたので、1か所にまとめました。
- `site-nav.css` / `site-nav.js` — 全ページ共通のナビゲーション。議会、議員・選挙、区政・財政、地域・参加、品川の歴史、検索・データ、公式サイトの7群です。機能へのリンクはピル形にし、現在地は塗りと `aria-current` で示します。スマートフォンでは折りたたみます。
- `site-controls.css` — 切り替えUIの語彙。囲みの有無が意味を持ちます。
- `site-mobile.css` — タップ領域、入力欄の文字サイズ、表の横スクロールなど、スマートフォン向けの共通調整です。
- `site-a11y.css` / `site-a11y.js` — 文字サイズ、配色、高コントラスト、動きを減らす設定、本文スキップリンク、端末内への設定保存を扱います。`site-a11y.js` は `<head>` で読み込み、本文の描画前に保存済み設定を適用します。

### 守っている約束

- **ナビゲーションはリンクを使う。** 共通メニューのピルは別ページやページ内の該当箇所への移動です。ページ内の切り替え操作には `site-controls.css` の部品を使います。
- **切り替えUIは3種類だけ。** 排他的な切り替えは`.seg`、絞り込みは`.chips`、年のように値が多いものは`.control-field`の`<select>`です。新しい形を増やさないでください。
- **`font-size`は必ず`calc(Npx * var(--fs))`で書く。** px直書きにすると、その要素だけ「表示設定 → 文字サイズ」が効かなくなります。
- **太さは400と700の2段階だけ。** 800や900は、可変フォントのない環境（Windowsの游ゴシック、AndroidのNoto Sans JP）では700に丸められて区別が消えます。
- **角丸は3px。** 丸ピルの999pxだけが例外です。
- **本文中のリンクの下線を消さない。** 色だけでリンクを示すと、色の見分けがつきにくい人に伝わりません（WCAG 1.4.1）。`.seg`や`.chips`のように囲みで操作だと分かるものは例外です。
- **配色には共通のカスタムプロパティを使う。** 標準・生成り・青みグレー・デモ配色・公共デザイン・ブルーと、高コントラストで表示を確認します。地図の区域や資料画像など、データの識別に使う色は各配色で共通です。

## 主なデータファイル

### 共通・人物

- `data/site.js` — 共通設定と年の一覧。各ページはこの`years`を見て年データを読み込みます。
- `data/members.js` / `data/former-members.js` — 現職・元職の区議名簿です。
- `data/politicians.js` — 現職・元職の都議、衆議、区長名簿です。
- `data/people.js` — 質問者と議員を紐付ける人物台帳で、表記揺れの名寄せにも使います。
- `data/speaker-members.js` — 会議録の発言者名（「安藤委員」）と議員IDの対応表です。自動生成で、議員ごとの年度索引も持ちます。

### 議会・行政

- `data/petitions.js` — 請願・陳情を受理番号で名寄せした自動生成台帳です。
- `data/petitions-official.js` — 公式ページから取得した付託委員会、受理年月日、議決結果です。
- `data/resolutions.js` — 公式「意見書・決議等」から取得した意見書、決議などです。
- `data/elections.js` — 品川区の選挙アーカイブデータです。
- `data/seimu.js` — 政務活動費の年度・会派・議員別公式資料です。
- `data/seijishikin.js` — 政治団体の収支報告書データです。
- `data/fiscal.js` — 予算・決算の年度別公式資料です。
- `data/gyosei.js` — 事務事業評価（政策評価の資料も含む）の年度別公式資料です。
- `data/jimujigyo-r07.js`・`-r06.js`・`-r05.js` — 令和7・6・5年度事務事業評価シートから読み取った小事業（652・669・665件）。`scripts/prepare_jimujigyo.py` が年度ごとに生成し、手で編集しない。件数と評価区分の内訳を各年度の公式集計と突き合わせる。年度をまたぐ同一事業は生成時に対応づけ、各事業に他年度の要約（`history`）を持たせる。年別データの全件ファイル（`data/rNN-complete.js`）から同じ年度・会計の予算議案を拾い、各年度データの `budgetBills` に持たせる。あわせて評価区分別・部署別の集計（`data/jimujigyo-summary.js`、数KB）を書き出し、`gyosei.html` が推移と部署別の表に使う。様式（用紙の向き・列の位置）が年度で違うので、列の境目は頁の見出しから決める。横断検索（`kensaku.html`）は検索語があるときだけ3年度分を読み込み、`kensaku-jimujigyo.js` で検索項目に変える。

### 品川の歴史

歴史コンテンツは、語彙と出典を1か所にまとめ、各レコードはそれを参照するだけにしています。
同じ資料名やURLを各レコードに書き写すと、資料のURLが変わったときに直し漏れが出るためです。

- `data/rekishi.js` — 時代区分、地区、カテゴリー、確実性、位置の種類、**出典台帳**、データファイルの一覧です。各レコードは `{ ref: "<出典ID>", locator: "該当箇所" }` で出典を参照します。
- `data/rekishi-events.js` — 年表のできごとです。
- `data/rekishi-people.js` — 人物です。
- `data/rekishi-areas.js` — 5地区の解説です。各地区に属するできごと・地点・人物の一覧は持たせず、画面側で数え上げます。
- `data/rekishi-names.js` — 地名の由来です。由来が確認できたものだけ `origin` に書き、確認できていないものは `null` のままにします。画面では「この資料では確認できていません」と明示します。地名の種類（現町名・旧村名・旧宿名・古道など）は `nameKind` で区別します。
- `data/rekishi-places.js` — 地図に載せる地点です。`scripts/prepare_rekishi_places.py` が品川区公式「指定文化財」から自動生成します。史跡・旧跡・建造物・天然記念物は1件を1地点にし、絵画・古文書などの動産は置かれている住所ごとにまとめて、その地点の `heritage` に並べます（1つの寺社に何本もピンが立たないようにするため）。

守っている約束は4つです。

1. **出典は台帳に1回だけ書く。** URLを持たない出典は、画面では破線の囲みにして押せないことを示します。
2. **関連は片側にだけ書く。** できごとが関連する人物を持ち、逆向きの参照は画面側で組み立てます。同じ関係を2か所に書かないので、片方だけ直して食い違う事故が起きません。
3. **地点IDは住所と名前から決める。** 通し番号にすると、公式ページに1行足されただけで以降のIDがすべてずれ、人物や年表から張ったリンクが黙って別の地点を指します。`pl-<sha1の先頭10桁>` にして、並び順が変わっても動かないようにしています。
4. **年が分からないものは確定させない。** `year` を `null` のままにし、`yearText` に「江戸時代初期」のように分かる範囲だけを書きます。並べ替えは時代区分の範囲から画面側で作り、データには書き戻しません。
5. **出典の無い項目は公開しない。** 確認が取れていないものは公開ファイルに入れません。

緯度経度は国土地理院の住所検索APIで求めますが、**答えをそのまま信じません。**
このAPIは番地まで見つからなくても近い単位の代表点を返すため、「荏原神社周辺」と
聞くと町の代表点が返り、荏原神社が実際にある北品川ではない場所にピンが立ちます。
`accept_geocode()` が「聞いた住所に番地の数字があること」と「返ってきた住所にも
数字があり町名が一致すること」を確かめ、通らないものは
`scripts/out/rekishi/pending.json`（git管理外・非公開）へ回します。

### 古地図・今昔比較

地図画像は配信元から読み込みます。[今昔マップ on the web](https://ktgis.net/kjmapw/tilemapservice.html) の「首都圏」から明治（1896〜1909年）と大正（1917〜1924年）の地形図を使い、南西原点のため Leaflet の `{-y}` を指定します。空中写真は[地理院タイル一覧](https://maps.gsi.go.jp/development/ichiran.html)の次の資料を使います。

| タイルID | 年代 | 形式 |
|---|---|---|
| `ort_riku10` | 1936〜1942年頃 | png |
| `ort_USA10` | 1945〜1950年（米軍撮影） | png |
| `ort_old10` | 1961〜1969年 | png |
| `gazo1` | 1974〜1978年 | jpg |
| `gazo2` | 1979〜1983年 | jpg |
| `gazo3` | 1984〜1986年 | jpg |
| `gazo4` | 1987〜1990年 | jpg |
| `seamlessphoto` | 全国最新写真（シームレス） | jpg |

旧版地形図はズーム16、戦前写真は18まで配信されています。
`maxNativeZoom` を指定しないと、それより拡大したとたんに写真が消えます。
指定しておくと最後の写真を引き伸ばして表示します。

「表示する地域」は、その地区の地点から範囲を作って地図を寄せます。地点が1件も
無い八潮地区は選べないようにしてあります。推測した座標でそれらしく動かすと、
根拠の無い位置を見せることになるためです。

### 地図の分類を足すときの約束

指定文化財の「種別」だけでは、ご依頼にあった10種類の対象のうち4種類しか
埋まりません（史跡・神社寺院・建造物・天然記念物）。残りは公式解説の
記述から読み取る必要があります。

**語句の一致で自動的に付けてはいけません。** 実際に試したところ、
「品川」の「川」で73件が水辺と判定され、「殖産興業」で由利公正の墓が
産業遺産になりました。`prepare_rekishi_places.py` の `CATEGORY_HINTS` に、
**1件ずつ公式ページの解説を読んで根拠を添えて手で書きます**。根拠は
`categoryNote` として出力し、地図の吹き出しに「なぜこの分類なのか」として
表示します。

所有者の欄が「－」の行があります（文政十一年銘道標（2））。そのまま地点名に
使うと地図に「－」というピンが立つので、`PLACEHOLDER` で弾いて文化財の名称に
振り替えます。

### 歴史マップの重なり

同じ住所の地点は同じ緯度経度になります。ピンを重ねて置くと下のピンが押せなく
なるため、`rekishi-map.html` は**座標ごとに1本のピン**にまとめ、吹き出しで
その場所にある地点をすべて並べます（北品川3-7-15には品川神社と3件の史跡が重なります）。
地図の右側には同じ条件で絞り込んだ一覧を出します。Leafletを読み込めない環境や、
キーボードだけで操作する場合でも同じ情報にたどり着けるようにするためです。

### 歴史データを腐らせないための仕組み

作ったあと放っておくと、2つの形で静かに劣化します。どちらも定期実行で見張ります。

| ワークフロー | いつ | 何をするか |
|---|---|---|
| `check-rekishi-links.yml` | 毎月16日 | 出典URL140本に順番にアクセスし、到達できないものを報告する |
| `collect-rekishi-places.yml` | 毎月2日 | 指定文化財を取り直し、検査を通ってから更新をコミットする |

**出典リンクの確認**（`scripts/check_rekishi_links.py`）は、`push` や
`pull_request` では動かしません。140件に順番にアクセスするので数分かかるうえ、
相手のサーバーの機嫌で落ちることがあり、変更と関係のないところで赤くなるためです。
一度の失敗では死んだと判断せず、間を置いてもう一度試します。403は自動アクセスを
断る設定のことがあるので、死んだ扱いにはせず警告として出します。

**件数が静かに減る事故を止める。** 公式ページの作りが変わると、解析が半分だけ
失敗して件数が減ることがあります。全滅なら気づけますが、「174件のうち20件しか
取れない」は気づきにくい。`prepare_rekishi_places.py` は、前回より1割を超えて
減ったときは書き出しを拒んで止まります（`shrank_too_much()`）。区が指定を
取り消した場合など、意図した減少のときは `--allow-shrink` を付けます。

監視そのものが鳴らなくなっていないかは `scripts/test_rekishi_links.py` の11件で
確かめます。通信はせず、`probe` を差し替えて判定の筋道だけを試します。

`scripts/check_rekishi_data.py` が、語彙の取り違え、IDの重複、壊れた相互リンク、
出典の欠け、緯度経度の取り違えを検査します。`scripts/test_rekishi_data.py` は、
その検査自体が働いていることを、わざと壊した仮のデータで確かめます。
どちらもGitHub Actionsの公開手順（`.github/workflows/pages.yml`）で実行します。

## 年データの読み込み

`data/site.js`の`years`は、会議録ページ（`kaigiroku.html`）と横断検索（`kensaku.html`）が年データを読み込むための共通一覧です。新しい年の追加方法は[データの更新方法](data-maintenance.md#過去年未来年の追加)を参照してください。

## 会議録全文の読み込み

委員会・本会議とも、要約や抜粋（索引）と全文は別の層に分かれています。

| 層 | ファイル | 読み込む単位 |
|---|---|---|
| 抜粋（委員会） | `data/<年>-committees-part-NN.js` | 年を選んだとき |
| 要約（本会議） | `data/<年>.js` / `<年>-complete.js` | 年を選んだとき |
| 全文の目次（本会議） | `data/<年>-plenary-minutes.js` | 年を選んだとき（数KB） |
| 全文 | `data/minutes/<年>/<会議ID>.js` | その会議の「会議録全文」を開いたとき |

全文は26年分で約470 MBあり、年単位でまとめて読み込むと1年約30 MBになって画面が開けません。委員会1回（平均約131 KB）・本会議1日（平均約119 KB）ずつに分け、読む意思表示があってから取りに行きます。

読み込みは`fetch()`ではなく`<script>`で行い、`window.SHINAGAWA_DB.registerMinutes()`へ登録します。`index.html`をダブルクリックして`file://`で開く使い方を残すためで、`fetch()`は`file://`ではCORSで止まります。ファイルの置き場所は会議IDから導けるため（`r06-20240515-19`→`data/minutes/r06/r06-20240515-19.js`）、対応表は持ちません。

委員会の抜粋は各質疑が`voiceIndex`（元の発言の位置、1始まり）を持ち、「原文を読む」から全文の該当発言（`#committee-<会議ID>-v0047`）へ移動できます。本会議は質問者ごとに、その議員が質問を始めた発言への入口（`#plenary-<会議ID>-v0008`）を持ちます。要約が見出しの言い換えで終わっていても、1手で原文に届くようにするためです。

会議IDの末尾で本会議（`r06-20240220-honkaigi`）と委員会（`r06-20240515-19`）を見分け、アンカーの接頭辞を切り替えます。設計の背景と容量の見積もりは[会議録全文の掲載設計](fulltext-minutes-plan.md)にあります。

## 議員ごとの質疑

本会議の`questions`は`memberId`を持ちますが、委員会の`exchanges[].speaker`は「安藤委員」「石田（ち）委員」のような姓＋役職の文字列だけで、議員IDがありません。議員ごとに質疑を横断するには、この文字列を議員IDに解決する必要があります。

**索引層に`memberId`は入れていません。** 入れると`data/<年>-committees-part-NN.js`約370本すべてが差分になり、容量も約4.8 MB増えます。代わりに対応表だけを`data/speaker-members.js`（32 KB）に出しています。

```js
speakerMembers["石田（し）委員"] = [
  ["2013-07-01", "2019-03-25", "x-ishida-shingo"],
  ["2023-05-26", "2025-06-09", "x-ishida-shingo"]
]
```

ある発言者名はある期間ずっと同じ1人に対応します（「田中委員」は2023年4月の区議選を境に切り替わるだけ）。26,434組の対応が285区間に畳めるのはこのためです。区間には終わりを持たせ、**実際に発言した日の外は答えません**。開始日だけだと最後の区間が未来永劫続き、落選して在職していない日にも議員IDを返してしまいます（石田しんごは2019〜2023年が落選期間）。

同じファイルに議員ごとの年度索引も入れています。`giin.html`はこれだけで「3,117件・16年度」と年度別の内訳を出せるので、年データ（1年6 MB）を読み込まずに済みます。

```js
memberQuestionIndex["hideo_ishida"] = { "h13": 45, "h14": 62, ... }
```

`kaigiroku.html`は`?member=<議員ID>&year=<年度ID>`を受け取り、その年の`exchanges`を`resolveSpeakerMember(speaker, dateIso)`で絞って並べます。本会議の`questions`（`memberId`つき）も同じ並びに混ぜ、日付の新しい順にします。選んだ質疑は出典URL付きのプロンプトになり、利用者自身の生成AIへ渡せます。サイトにAIは載せず、作るのはプロンプトの文字列までです。

対応表の作り方と検査は[データの更新方法](data-maintenance.md)にあります。

## リンクの種類と色

| 型 | 色 | 用途 |
|---|---|---|
| `official` | 青 | 公式資料・日程へのリンク |
| `video` | 赤 | インターネット中継の録画へのリンク |
| `minutes` | 緑 | 会議録検索システムの正式版へのリンク |
| `minutesDraft` | 緑 | 校正原稿PDFへのリンク |

`minutesDraft`の校正原稿PDFは、正式版公開後に公式サイトから削除される場合があるため、該当リンクがある場合は注意案内を表示します。

## スマートフォンとアクセシビリティ

- サイトの全14ページを対象に、幅320px以上でページ全体の横方向のはみ出しが出ないよう調整しています。
- 画面幅640px以下では、共通ナビゲーションの14リンクを「☰ メニュー」にまとめ、現在のページ名をボタンに表示します。
- 入力欄と選択欄は16px以上とし、iOSで操作時に画面が自動拡大しにくいようにしています。
- 選挙結果など横に長い表は、案内を表示したうえで表だけを横スクロールできるようにしています。
- ボタンとリンクには原則44px以上の操作領域を確保しています。
- 文字サイズ、配色、高コントラスト、動きを減らす設定は同じ配信元のページ間で引き継ぎます。GitHub Pages と、ニュース・イベントを配信する Firebase Hosting ではそれぞれの配信元に保存します。
- パソコン向け表示では、折りたたみメニューは表示しません。
